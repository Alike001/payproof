# Reference Repository Index

Snapshot date: **2026-08-31**.

These are shallow, commit-pinned research clones used to study product flows,
architecture, implementation depth, and common hackathon shortcuts. They are
not dependencies of the future Telegraph application.

Most repositories in this collection do **not** have a repository-wide open
source license. Public visibility on GitHub is not permission to copy code.
Unless a compatible license clearly covers the relevant file, use only the
general product and architecture lessons.

## Important implementation-reality findings

- ProofGate already implements the core of an agent URL firewall. A new
  `URL_SCAN`-only Track 3 app would have weak differentiation.
- The checked-in x402 Guard proxy uses a placeholder `X-PAYMENT` proof and a
  mock target API. Its Solidity approval path queues a payment and then reverts;
  the revert rolls the queue write back. Treat its policy vocabulary as a
  product reference, not a working payment implementation.
- AgentX402 uses a fixed three-product dataset and commits an environment file
  and Python cache files. Its handoff diagram is useful; its repository hygiene
  is not a model to follow.
- Defensive Security automates WHOIS lookup, but its other safety checks are
  manual toggles. The idea is broader than the implementation.
- Blackbelt's risk-score factors are understandable, but the repository still
  contains placeholder IPFS output and sample-template tests.
- LastCheck has a clear rules/ask/reject flow but no focused automated tests in
  the inspected snapshot.
- RainGuard won a Chainlink prize, but the inspected settlement contract still
  calls an internal mock oracle result and its contract test folder only tests
  the Scaffold-ETH sample contract. Reuse the lifecycle lesson, not its claims
  of production completeness.
- Aegis402 has the strongest inspected evidence discipline: explicit schemas,
  deterministic normalization, risk bands, fixtures, unit tests, and a narrow
  statement of what is out of scope.
- Forta's MIT examples demonstrate a good minimal standard: one detection rule,
  one structured finding, and tests for both the positive and negative cases.
- The official submission repository still models only `miner` and `wasm`
  entries, and its Track 3 UI is still marked coming soon in the inspected
  commit. It is not yet evidence of prior Telegraph application submissions.
- Am I Cooked is the strongest inspected consumer-product reference: one pasted
  wallet, a memorable verdict, a useful next action, alarms, public cards, and
  focused tests. Demo replays are explicitly labeled instead of silently
  replacing failed live data.
- Horacle's human-answer marketplace has a strong one-question and push-alert
  loop, but its clients can fall back to an unpaid path when payment fails and
  one payment module contains a hard-coded RPC credential. Copy the product
  simplicity, not those implementation choices.
- SkyFall and Hide&Seek both demonstrate the danger of combining too many
  product surfaces. Their inspected repositories contain multiple mock,
  placeholder, or incomplete execution paths.
- Vigil's monitor-to-call/email/report flow is reusable, but its scraped-data
  and pseudo-embedding fallbacks must be disclosed if a similar fallback is
  ever used.
- ClankerCatcher's checked-in backend marks media verified through placeholder
  logic. ZK Microphone has much stronger provenance depth, but Telegraph's
  related media Intents are live-only, thinly supplied, and not in the official
  40-Intent catalog.
- CrossMeter proves that a clean checkout can hide chain complexity, but its
  public checkout falls back to mock payment intents after API failure.
  EthMail's inspected UI uses sample balances and a fixed payment amount.
- Omni402 has the deepest payment architecture in the new comparison, including
  contracts, a facilitator, an SDK, verification, and deployed-address claims.
  Its breadth is far beyond a seven-day Track 3 application and should not be
  recreated.
- Split's most reusable lesson is the familiar `photo -> understand -> divide
  -> settle` journey. Its backend has an explicit mock mode switched off by
  default; the new Telegraph product should likewise fail visibly rather than
  silently fabricate a successful result.

## Clone policy

Do not edit these folders as part of the Telegraph application. Build the new
project outside this directory and record any consciously reused MIT/MPL code
with its required notices.
